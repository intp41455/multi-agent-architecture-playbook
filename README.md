# 企业多智能体架构落地方法论

> 从「业务制度」到「确定性执行」的方案设计方法论。
> 不含任何具体企业数据；结论来自公开框架文档与自建系统的工程实践。

---

## 这份文档解决什么问题

企业想把多智能体用起来，通常卡在三个地方：

| 卡点 | 表现 | 根因 |
|---|---|---|
| **不敢用** | 让 AI 算工资、碰健康档案、签审批，没人敢签字 | 决策权被让渡给了概率型算法 |
| **不会选** | CrewAI / LangGraph / Dify / 自研，选型靠"听说谁火" | 没按「业务确定性要求」和「数据敏感度」匹配 |
| **落不了地** | POC 演示很漂亮，上生产两周就崩 | 没有审计、没有熔断、没有人工兜底位 |

本文给三样东西：**安全边界怎么划、框架怎么选、审计怎么做**。

## 0. 一句话方法论

> **AI 提供可能性，代码提供确定性。**

把这句话拆成可执行的动作，就是下面五节。

---

## 1. 左移确定性 —— 安全边界的划法

传统做法是"运行期加护栏"：模型先自由推演，出问题再拦。
问题在于，概率型算法在运行期的输出是**不可枚举的**，你无法穷举所有拦截条件。

正确做法是把确定性**向左移动到工程前期**：

```
业务制度原文
    ↓ 人工梳理 + 核准（这一步花 100% 的力气）
刚性规则库（JSON Schema / 状态机）
    ↓ 模型只做一次「自然语言 → 结构化」的翻译
标准化输入
    ↓ 本地死代码执行（确定性）
执行结果
```

**关键约束**：模型只负责"翻译"，不负责"计算"。

- ✅ 模型可以输出 `{"name":"张三","事假":1}`
- ❌ 模型不可以输出"张三实发 5758.62 元"

后者必须由本地脚本按写死的四则运算算出，即使模型算对了也不采纳——因为**无法验证它下次是否还这么算**。

### 1.1 双门模型：云端管"嘴"，本地管"手"

很多企业开发者有个误解：用了头部厂商的 API，厂商会替你兜底安全。实际上云端与本地之间有一条不可混淆的边界：

| | 第一道门：内容护栏 | 第二道门：执行护栏 |
|---|---|---|
| **约束对象** | 模型的「嘴」（生成的文本） | 操作系统的「手」（代码执行） |
| **控制权** | 服务商云端 | **本地部署者** |
| **能拦住什么** | 违禁内容、初级提权指令 | 越权写入、越权 API 调用 |
| **拦不住什么** | 结构化隐藏的恶意指令 | 开发者主动写 `os.system(模型输出)` |

**注意**：模型通过 API 返回一段合法 JSON 时，内容护栏会判定为合法通过。
真正的风险点在第二道门——如果本地代码写了 `os.system(模型建议)` 且一路同意，流量就从本地路由器发出去了。

**治理铁律**：永远把模型当「输入法」（只提建议值），不当「操作系统」（不给直接系统指令权限）。
所有文件写入与网络请求，必须经过本地写死的白名单。

## 2. 多智能体分工 —— 三角色 + 红线约束

单智能体做复杂业务，问题不是"能力不够"，而是**它既当运动员又当裁判**。
分工的意义不是提升效率，而是**制造互相制衡**。

以「薪资考勤自动化」为例（最容易验证、也是幻觉代价最高的场景）：

```
① 原始输入        ② 需求解析师        ③ 精算执行员        ④ 审计监察员        ⑤ 财务落表
打卡流水/请假单  →  非结构化 → JSON  →  套用刚性公式   →  环比/抽样/异常   →  写入新文件
                   (只解析，不算数)     (只出数字，不解释)   (只裁决，不改数)     (不覆盖原件)
```

### 三个角色的红线（这部分是设计的核心）

| 角色 | 职责 | 红线 |
|---|---|---|
| **需求解析师** | 解析口语化打卡记录与备注，识别请假类型与时长 | **严禁进行任何工资或扣款计算** |
| **精算执行员** | 接收结构化 JSON，按刚性公式级联运算 | **只输出纯数值，禁止生成文字解释** |
| **审计监察员** | 环比波动比对、抽样复验、逻辑反常拦截 | **判定为 BLOCK 时，禁止调用下游写入引擎** |

三条红线合起来，保证了一件事：**任何一步的模型都碰不到全链路的完整权限**。

### 2.1 刚性公式池：把"业务口径"变成"参数表"

企业制度的复杂性不该用 prompt 表达，应该用参数表表达：

| 核算项 | 公式 | 合规依据 |
|---|---|---|
| 法定日薪 | `日薪 = 底薪 ÷ 21.75` | 法定月计薪天数折算 |
| 事假扣减 | `事假天数 × 日薪 × 100%` | 全额扣减无薪工时 |
| 病假扣减 | `病假天数 × 日薪 × 40%` | 按 60% 日薪计发 |
| 迟到阶梯 | 1–15 分钟 20 元；16–60 分钟 50 元；>60 分钟扣半天日薪 | 阶梯式约束 |
| 旷工 | `旷工天数 × 日薪 × 3` | 遏制未审批脱岗 |
| 五险一金 | `缴费基数 × (个人比例 + 公积金比例)` | 税前统筹扣减 |

**为什么用参数表而不是 prompt？**
因为参数表可以被审计——每一行都有出处、可以被 HR 复核、可以在后台改而不改代码。
参考实现见 [`templates/payroll_engine_example.py`](templates/payroll_engine_example.py)（约 20 行，本地离线运行，无需暴露任何 API 密钥）。

## 3. 框架选型 —— 六方横评

选型标准不是"参数最强"，而是**业务确定性要求 × 数据敏感度**。

先按形态分类——市面上顶着 "Agent" 名字的工具，其实不是一类东西：

| 类别 | 隐喻 | 代表 |
|---|---|---|
| 开发编排底座 | 乐高积木 | LangGraph、CrewAI |
| 低代码平台 | 成品套件 | Dify、扣子 |
| 自主智能体 | 数字员工 | Hermes / OpenClaw 类 |
| 企业级应用 | 开箱即用的专家团 | 各类内置行业角色的桌面端产品 |

再逐项打分（**可控度 = 流程可预测、可回滚；安全性 = 权限收敛程度**）：

| 框架 / 平台 | 类别 | 定位 | 可控度 | 安全性 | 适用场景 |
|---|---|:---:|:---:|:---:|---|
| **LangGraph** | 开发框架 | 基于有向循环图（Cyclic Graph）的工业级编排底座 | 10 | 9 | 财务、医疗等对**状态回滚、断点续跑**要求极高的生产环境 |
| **CrewAI** | 开发框架 | 基于角色扮演（Role-Playing）的多智能体敏捷协作 | 8 | 8 | 职责清晰、需要快速打样验证的业务团队 |
| **Dify / 扣子** | 低代码平台 | 拖拽式画布 + 可视化工作流 | 7 | 7 | 业务骨干主导的内部流程，不希望写重工程代码 |
| **Harness** | DevOps 平台 | 嵌入 CI/CD 的 AI 审查门禁 | 9 | 10 | 研发团队的 PR 合规审查、自动化漏洞修复 |
| **Hermes 类** | 自主智能体 | 长程记忆 + 工具自主调用 | 5 | 4 | 极客个人工作流自动化、自托管研发助手 |
| **企业级桌面产品** | 企业应用 | 内置行业专家的成熟产品 | 7 | 8 | 中大型企业通用办公协同与方案研讨 |

### 3.1 黄金三角混合部署：本地骨架 + 云端插件 + 规则引擎

不用非此即彼。生产环境的最优解通常是三层混合：

| 层 | 放什么 | 理由 |
|---|---|---|
| **本地核心骨架** | 敏感数据（薪资、健康档案、财务凭证）100% 留在私有容器，物理不出域 | 数据主权底线。由本地小模型或死代码负责清洗与私有计算 |
| **云端智能插件** | 需要理解长法律条文、新政解读、复杂推理时，抛**完全去标识化**的抽象文本给云端最强模型 | 只要结论，不带原文。拿能力上限，不交数据主权 |
| **精细化规则引擎** | 企业所有"个性化规则"（哺乳期打卡宽容、异地调休系数…）写死在确定性工作流 | 大厂通用产品不会为你微调——**这是企业不可替代的数字护城河** |

## 4. 审计体系 —— 3-Tier Audit

多智能体上生产，最怕的不是"答错"，而是**"答错了没人知道"**。
审计必须分层，每层有不同的触发时机和准入标准。

### TIER 01 · 落地前：数字孪生沙盘推演

抽取过去 6 个月的**脱敏**真实数据，人工构造 50+ 极端边界案例（如关键指标骤降、节假日排班真空、多地负责人同时空缺）。

监察 Agent 在封闭沙箱中模拟执行，比对 AI 裁决与人类历史处理结果。

> **准入标准**：常规场景一致性 ≥ 95%，**且** 5% 极端边缘场景全部被安全拦截并触发人工兜底预案——方可进入开发阶段。

### TIER 02 · 运行中：三明治交叉验证

每次任务流转时实时触发三道校验：

| 校验层 | 检查内容 |
|---|---|
| **结构性校验** | 字段无缺失、Schema 完全合规 |
| **逻辑自洽性** | 跨 Agent 数据勾稽关系无矛盾（如报到率与打卡人数冲突） |
| **时效新鲜度** | 时间戳未超期，杜绝陈旧日志误判 |

> **准入标准**：三盏绿灯齐亮，下游写入模块才拿到执行锁；任一失败立刻原地刹车。

### TIER 03 · 周期复盘：反馈闭环

跟踪两个核心指标，按月复盘：

- **建议采纳率**（目标 75%）—— 衡量 AI 输出是否真的被业务用起来
- **合规审计误报率**（目标 ≤ 2%）—— 衡量审计层是否在制造噪音

同时做三件事：消除歧义规则、季度评测新开源模型、规则库热插拔补丁。

## 5. 异常分级与熔断

分级响应，避免"一刀切停机"和"一律放过"两个极端：

| 级别 | 触发条件 | 系统动作 | 人工介入 |
|:---:|---|---|---|
| **L1 轻微** | 单点非关键字段缺失 | 记审计日志 → 推送轻提醒 → 次日自动重试 | 不需要，自愈或顺延 |
| **L2 一般** | 输出格式损坏 / 字段与 Schema 不符 / 勾稽矛盾（如实发环比突变 20%） | 挂起该子 Agent → 重试 1 次 → 仍异常则阻断下游并告警 | 业务主管登录看板看差额明细，点「确认放行」或「驳回重算」 |
| **L3 严重** | 核心数据连续中断 / 多 Agent 输出严重悖论 / 疑似提示词注入或越权指令 | **物理熔断**：封锁所有对外 API、冻结本地写入、系统回退只读 | 必须架构师 + 分管负责人**双人独立密钥**方可解封 |

**L3 的设计要点是"双人密钥"**——单点可以关掉系统，但不可以单点打开系统。

## 6. 落地调研 —— 10 维度问卷

方案质量的上限，取决于调研深度。建议立项前 1–2 周下发，7–10 个工作日回收。

完整可填写模板见 [`templates/10-dimension-questionnaire.md`](templates/10-dimension-questionnaire.md)。

| # | 维度 | 核心问题数 |
|:---:|---|:---:|
| 1 | 企业基本信息与数字化现状 | 4 |
| 2 | 组织架构与人员画像 | 2 |
| 3 | 各业务板块微观数据详情 | 2 |
| 4 | 现有 IT 基础设施与数据治理环境 | 2 |
| 5 | 业务规则、标准化体系与异常边界 | 2 |
| 6 | 外部数据、政策监控与行业对标 | 2 |
| 7 | 合规安全、数据主权与物理隔离 | 2 |
| 8 | 用户交互偏好与体验设计需求 | 2 |
| 9 | 技术约束、模型选型与集成偏好 | 2 |
| 10 | 投资预算、里程碑与验收标准 | 2 |

### 一个容易被忽略的设计：数据精度三级标注

要求填报方对每个数字标注来源等级，**避免"估算值被当成法定数据用于核算"**：

| 标注 | 含义 |
|---|---|
| `[精确]` | 系统直接导出或财报可查的法定数据 |
| `[估算]` | 经业务主管交叉核实的合理运营预估值 |
| `[初步]` | 未经核验的定性推测，立项后需专项调研 |

## 适用范围与边界

**适用**：企业内部有明确制度文本、流程重复度高、错误代价高、数据敏感的自动化场景（人事、财务、合规、质控）。

**不适用**：
- 创意类、开放式任务（确定性本身就是负担）
- 没有制度文本沉淀的领域（规则库无从梳理）
- 追求"全自动无人化"的场景——本文所有方案都保留人工兜底位，**目标不是无人，而是把人的精力从重复核对转移到异常裁决**
