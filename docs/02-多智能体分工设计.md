# 02 · 多智能体分工设计

> 本章解决：**为什么要把一件事拆给三个 Agent 做，而不是用一个更强的模型？**

---

## 2.1 分工的意义不是效率，是制衡

单智能体做复杂业务，问题往往不是"能力不够"，而是**它既当运动员又当裁判**。

一个模型同时负责"理解需求"和"计算结果"，会出现两种失效模式：

1. **幻觉传导**：第 3 步的理解偏差，被第 7 步当成事实继续推导，最后产出一个自洽但错误的结果
2. **责任不可定位**：出错后无法判断是理解错了、算错了、还是规则本身有歧义

拆成多个角色后，每个环节的输入输出都被**显式契约**约束，偏差会在环节边界被拦下来。

**所以分工的第一收益是"可定位"，第二才是"可并行"。**

---

## 2.2 三角色架构（以薪资考勤精算为例）

选这个场景做示例，是因为它同时满足三个条件：规则可穷举、错误代价高、幻觉最容易发生。

```
① 原始输入          ② 需求解析师          ③ 精算执行员         ④ 审计监察员        ⑤ 财务落表
钉钉导出打卡单   →   非结构化 → JSON    →   套用刚性公式     →   环比/抽样/反查   →   写入新文件
请假审批备注        (只解析，不算数)      (只出数字，不解释)    (只裁决，不改数)     (不覆盖原件)
    │                    │                     │                    │                  │
  人工导出            输出 JSON Schema      输出纯数值          输出 PASS/BLOCK     人工抽验签字
  与预脱敏
```

### 角色定义与红线

#### 角色一 · 需求解析师（Data Translator）

| 项 | 内容 |
|---|---|
| **模型定位** | 强理解、长上下文（如 DeepSeek-V3 类） |
| **核心职责** | 解析口语化打卡记录与备注；识别请假类型（年假/病假/事假/调休）与实际生效时长；提取有效考勤标签 |
| **输出契约** | 严格 JSON Schema，字段固定 |
| **红线** | **严禁进行任何工资或扣款计算** |

为什么这条红线必要：解析师能看到原始文本，如果允许它"顺手算一下"，它就会基于模糊理解给出数字，而这个数字会污染下游。

#### 角色二 · 精算执行员（Computation Engine）

| 项 | 内容 |
|---|---|
| **模型定位** | 强逻辑、强结构化输出（如 Claude 类） |
| **核心职责** | 接收结构化 JSON；严格按计薪天数（21.75）、日薪公式、扣款率完成级联运算；执行全勤奖发放条件判断 |
| **输出契约** | 只输出纯结构化数值 |
| **红线** | **禁止生成文字解释** |

为什么禁止解释：一旦允许输出文字，模型会用文字"圆"一个算错的数，审计层就失去了判断依据。数值对错，交给审计层用基线比对。

#### 角色三 · 审计监察员（Audit Inspector）

| 项 | 内容 |
|---|---|
| **模型定位** | 高性价比、强约束（如 GPT-4o-mini 类） |
| **核心职责** | 提取历史月度基准做环比波动审查（阈值 ±20%）；校验出勤率合理性；对 2–3 人做抽样复验（容差 0.01 元即拦截） |
| **输出契约** | `PASS` / `BLOCK` + 裁决单 |
| **红线** | **判定 BLOCK 时，绝对禁止调用下游 Excel 生成引擎** |

这条红线是整个架构的安全阀：审计层不负责"修正"，只负责"拦住"。

### 三条红线的共同作用

> 任何单个 Agent 都拿不到全链路的完整权限。

| | 能看到原始数据 | 能计算 | 能写文件 |
|---|:---:|:---:|:---:|
| 需求解析师 | ✅ | ❌ | ❌ |
| 精算执行员 | ❌ | ✅ | ❌ |
| 审计监察员 | ❌ | ❌（只复验） | ❌（只裁决） |
| 本地落表脚本 | ❌ | ✅ | ✅ |

## 2.3 刚性公式池：把「业务口径」变成「参数表」

企业制度的复杂性**不该用 prompt 表达，应该用参数表表达**。

### 为什么不用 prompt

| | Prompt 表达 | 参数表表达 |
|---|---|---|
| 可审计 | 难（散落在文字里） | ✅ 逐行有出处 |
| 可复核 | 需要懂 prompt | ✅ 业务方能读 |
| 可修改 | 需重新调教模型 | ✅ 改数据即可 |
| 可回滚 | 难 | ✅ 版本化 |

### 参数表示例（结构示意）

| 核算项 | 公式 | 合规依据 |
|---|---|---|
| 法定日薪 | `日薪 = 底薪 ÷ 21.75` | 法定月计薪天数折算 |
| 事假扣减 | `事假天数 × 日薪 × 100%` | 无薪事假全额扣减 |
| 病假扣减 | `病假天数 × 日薪 × 40%` | 按 60% 日薪计发 |
| 迟到阶梯 | 1–15 分钟 20 元 / 16–60 分钟 50 元 / >60 分钟扣半天日薪 | 阶梯式约束 |
| 旷工 | `旷工天数 × 日薪 × 3` | 遏制未审批脱岗 |
| 五险一金 | `缴费基数 × (社保个人比例 + 公积金比例)` | 税前统筹扣减 |

**每一个数字都要有出处**——这是"可审计"的前提，也是审计层能工作的基础。

参考实现见 [`templates/payroll_engine_example.py`](../templates/payroll_engine_example.py)：约 20 行，本地离线运行，不需要暴露任何 API 密钥。

## 2.4 跨 Agent 的通信契约

角色拆开了，接口就必须定死，否则制衡会退化成扯皮。

### 三条契约原则

**① 只传结构化数据，不传自然语言**

```json
// ✅ 好的契约
{"name": "张三", "事假天数": 1, "病假天数": 0, "迟到次数": 2, "旷工天数": 0}

// ❌ 坏的契约
{"备注": "张三这个月请了一天事假，迟到两次，其他正常"}
```

后者把解析责任又推回给了下游。

**② 字段缺失必须显式声明，不能靠默认值**

```json
{"name": "张三", "事假天数": 1, "_missing": ["调休天数"]}
```

静默补 0 是危险的——"这个字段是 0"和"这个字段没提供"是两件事。参考第 05 章提到的"静默失败是债务"。

**③ 每次流转携带溯源信息**

至少包含：任务 ID、上游 Agent 标识、数据时间戳。
时间戳用于第 04 章的"时效新鲜度"校验。

## 2.5 常见设计错误

| 错误 | 后果 | 正确做法 |
|---|---|---|
| 让解析 Agent 顺手算数 | 模糊理解污染数值 | 红线禁止，算数一律交给执行层 |
| 让执行 Agent 解释结果 | 用文字圆错误结论 | 只输出数值，对错交审计层判定 |
| 让审计 Agent 顺便修正 | 审计层失去独立性 | 只裁决 PASS/BLOCK，不修改数据 |
| 多个 Agent 共享上下文记忆 | 偏差互相传导，制衡失效 | 每个 Agent 独立上下文，只通过契约通信 |
| 下游覆盖上游文件 | 异常时无法回溯 | 每步写新文件，原件只读 |

---

## 本章小结

| 原则 | 一句话 |
|---|---|
| 分工目的 | 第一是"可定位"，第二才是"可并行" |
| 权限切分 | 单个 Agent 拿不到全链路完整权限 |
| 业务口径 | 用参数表表达，不用 prompt 表达 |
| 通信契约 | 只传结构、缺失显式声明、每次带溯源 |
| 审计独立 | 审计不修正，只拦截 |
