# 03 · 框架选型横评

> 本章解决：**CrewAI / LangGraph / Dify / 自研，到底选哪个？**

---

## 3.1 选型标准只有两个变量

不是"参数最强"，而是：

```
业务确定性要求  ×  数据敏感度
```

- **确定性要求高**（财务、医疗、合规）→ 优可控度，允许牺牲上手速度
- **数据敏感度高**（人事薪资、健康档案）→ 优可私有化部署，允许牺牲模型能力

其它因素（社区热度、文档质量、Star 数）是次要的——**选错形态的代价，远大于选错具体产品**。

---

## 3.2 先分类：叫 "Agent" 的东西不是一类

市面上顶着 "Agent" 名字的工具，形态差异极大。按形态分四类：

| 类别 | 隐喻 | 代表 |
|---|---|---|
| **开发编排底座** | 乐高积木 | LangGraph、CrewAI |
| **低代码平台** | 成品套件 | Dify、扣子 |
| **自主智能体** | 数字员工 | Hermes / OpenClaw 类 |
| **企业级应用** | 开箱即用的专家团 | 内置行业角色的桌面端产品 |

**这一步分类比打分更重要**：拿"开发框架"和"低代码平台"比易用性，或拿"自主智能体"和"CI 门禁"比可控度，都是无效对比。

---

## 3.3 六方横评

两个评分维度定义清楚：

- **可控度**：流程是否可预测、可回滚、可断点续跑（10 = 完全确定性）
- **安全性**：权限收敛程度、数据可否不出域（10 = 最小权限 + 完全私有）

| 框架 / 平台 | 类别 | 核心隐喻与定位 | 可控度 | 安全性 | 最适合场景 |
|---|---|:---:|:---:|:---:|---|
| **LangGraph** | 开发框架 | 像绘制精细的状态流转图：基于有向循环图（Cyclic Graph）的工业级编排底座 | **10 / 10** | 9 / 10 | 金融、医疗、财务等对**流程确定性、状态回滚、断点续跑**要求极高的生产环境 |
| **CrewAI** | 开发框架 | 像导演组建剧组：基于角色扮演（Role-Playing）的多智能体敏捷协作 | 8 / 10 | 8 / 10 | 职责清晰、分工明确、需要快速打样验证的业务团队 |
| **Dify / 扣子** | 低代码平台 | 像搭乐高积木：拖拽式画布 + 可视化全功能工作流 | 7 / 10 | 7 / 10 | 产品经理、业务骨干主导的内部管理流程，不希望写重工程代码 |
| **Harness** | DevOps 平台 | 像严谨的发布质检官：嵌入 CI/CD 管线的 AI 代码审查与安全门禁 | 9 / 10 | **10 / 10** | 研发团队的软件交付管线、PR 合规审查、自动化漏洞修复 |
| **Hermes 类** | 自主智能体 | 像聘一位全能个人助理：具备长程持久记忆与自主工具调用 | **5 / 10** | **4 / 10** | 个人工作流自动化、自托管研发助手、环境探针 |
| **企业级桌面产品** | 企业应用 | 像开箱即用的专家智囊团：内置多行业专家角色的成熟产品 | 7 / 10 | 8 / 10 | 中大型企业通用办公协同与方案研讨 |

### 读法说明

**LangGraph 可控度给 10**，因为状态是显式的、图是静态定义的、每一步都能持久化和回滚——这三点对"算钱"的场景是刚需。

**Hermes 类安全性给 4**，不是因为它做得差，而是它的设计目标就是"能自主操作电脑"——**能力上限高和权限收敛本来就是矛盾的**。放在个人环境里是优点，放在生产财务系统里就是风险。

**Harness 安全性给 10**，因为它不做决策，只做门禁——权限最小化做到了极致。

## 3.4 不用非此即彼：黄金三角混合部署

生产环境的最优解通常是**三层混合**，而不是选一个框架包打天下。

```
┌─────────────────────────────────────────────────────┐
│  ③ 精细化规则引擎（核心壁垒）                          │
│     企业所有"个性化规则"写死在确定性工作流中              │
│     例：哺乳期打卡宽容、异地调休系数、特殊岗位豁免          │
├─────────────────────────────────────────────────────┤
│  ② 云端智能插件（能力上限）                            │
│     需要长条文理解、复杂推理时，抛完全去标识化的抽象文本     │
│     只回收结论文本，不交出原文                          │
├─────────────────────────────────────────────────────┤
│  ① 本地核心骨架（安全底线）                            │
│     敏感数据 100% 留在私有容器，物理不出域                │
│     由本地开源模型或死代码负责清洗与私有计算               │
└─────────────────────────────────────────────────────┘
```

### 三层的分工理由

| 层 | 放什么 | 为什么 |
|---|---|---|
| **本地核心骨架** | 薪资明细、健康档案、财务凭证、客户隐私数据 | 数据主权底线。这部分物理不出域，不讨论"是否加密传输" |
| **云端智能插件** | 需要理解长法律条文、政策解读、高难度推理的任务 | 拿能力上限，不交数据主权。前提是**完全去标识化**——抽象掉所有可定位到具体人的信息 |
| **精细化规则引擎** | 企业全部个性化业务规则 | 大厂通用产品永远不会为你微调。**这是企业不可替代的数字护城河** |

### 一个容易被忽略的判断

第 ③ 层的价值常被低估。很多企业把"个性化规则"当成"系统缺陷"（"为什么标准产品不支持我们的算法？"），事实上恰恰相反——

> 通用产品覆盖得越广，就越不可能为你的特殊口径做适配。
> 那些只能靠人工经验传递的规则，一旦被结构化成规则库，就从"依赖某个老员工的记忆"变成"组织的资产"。

## 3.5 选型决策树

```
你的场景……
│
├─ 要处理的是一笔钱 / 一条命 / 一份合规文件？
│   └─ 是 → 确定性优先
│        ├─ 需要状态回滚、断点续跑？ → LangGraph
│        └─ 团队无重工程能力？      → Dify，但必须外挂规则引擎做核算
│
├─ 数据能不能出内网？
│   └─ 不能 → 排除所有纯 SaaS 方案；本地骨架 + 云端插件混合
│
├─ 只是想让业务同事快速试一个流程？
│   └─ 是 → Dify / 扣子，先跑通再谈架构
│
└─ 想让 AI 自主操作电脑完成开放任务？
    └─ 是 → 自主智能体类，但**必须隔离在专用环境**，不接入生产数据
```

---

## 3.6 三个常见的选型误判

| 误判 | 表现 | 后果 |
|---|---|---|
| **按 Star 数选** | "这个框架 60k star，肯定好" | Star 数反映社区热度，不反映流程可控度 |
| **按 Demo 效果选** | 看一个漂亮的演示视频就拍板 | Demo 通常避开了异常分支，而生产环境的 90% 工作量在异常处理 |
| **追求"一个框架解决全部"** | 硬要用低代码平台做财务核算 | 形态不匹配——低代码的强项是"快速改流程"，弱项是"确定性保证" |

**最贵的选择不是选错了框架，而是选了一个形态不匹配的框架，然后在上面打补丁打了半年。**

---

## 本章小结

| 原则 | 一句话 |
|---|---|
| 选型变量 | 业务确定性要求 × 数据敏感度 |
| 先分类 | 开发框架 / 低代码 / 自主智能体 / 企业应用，不是一类东西 |
| 混合优于单选 | 本地骨架 + 云端插件 + 规则引擎 |
| 规则引擎 | 个性化规则是护城河，不是缺陷 |
| 最大成本 | 形态错配后的长期打补丁 |
