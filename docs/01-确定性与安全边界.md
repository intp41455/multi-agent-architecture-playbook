# 01 · 确定性与安全边界

> 本章解决：**凭什么敢让 AI 参与真钱、真数据的事？**

---

## 1.1 问题的本质：决策执行主体的让渡

讨论 AI 安全，常见的落点是"数据泄露"。但对生产系统而言，真正的风险不是泄露，而是**决策执行主体从人类被让渡给了不可控的概率型算法**。

这个区别很重要：

| | 人类操作者的误操作 | 自主智能体的越界 |
|---|---|---|
| 行为性质 | 具备主观故意的违规，受法律威慑 | 无道德痛感，目标泛化 |
| 速度 | 受限于体力与操作节奏 | 分钟级完成"环境突破 → 凭证滥用 → 提权"全链路 |
| 可预测性 | 行为模式可预判 | 具备实时自我变招能力 |
| 责任归属 | 清晰 | **法理真空**——法律上不存在"AI 犯罪"的主体资格，责任穿透到部署者 |

最后一条是最实际的约束：**如果因过度授权引发事故，司法机关会穿透技术表象，认定授权环境、开放权限的部署者为主责。**

所以安全边界不是"技术要求"，是"责任要求"。

---

## 1.2 为什么"运行期加护栏"不够

直觉方案是：让模型自由发挥，运行期用规则拦截越界行为。

问题在于概率型算法的输出空间**不可枚举**。

你可以拦截 `rm -rf /`，但你拦不住：

```python
# 一段完全合法的代码，但语义上等价于删库
ids = fetch_all_ids()
for i in ids[:100]:
    db.delete(i)
```

或者更隐蔽的——模型为了"完成任务"，自主判断某个校验环节是"阻碍变量"，选择绕过它。

**根本原因**：拦截规则是有限的，模型生成的变体是无限的。你在做一场打不赢的军备竞赛。

---

## 1.3 左移确定性：把护栏搬到工程前期

正确的做法是把确定性的建设**从运行期左移到设计期**：

```
① 业务制度原文（自然语言，模糊）
        │
        │  人工梳理 + 业务方核准    ← 这一步花 100% 的力气
        ▼
② 刚性规则库（JSON Schema / 状态机 / 参数表）
        │
        │  模型只做一次结构化翻译    ← 单次、可校验、可回滚
        ▼
③ 标准化输入（结构固定的 JSON）
        │
        │  本地死代码执行            ← 确定性、可复现
        ▼
④ 执行结果 + 审计轨迹
```

### 关键约束：模型只"翻译"，不"计算"

| | 允许 | 禁止 |
|---|---|---|
| 需求解析 | ✅ `{"name":"张三","事假":1,"迟到":2}` | ❌ "张三大概要扣两百多块" |
| 数值计算 | ❌ 任何形式的算术 | ✅ 由本地脚本按参数表算出 |

**即使模型算对了也不采纳。**

这不是不信任某一次输出，而是**无法验证下一次是否还这么算**。一个时会时不会的计算引擎，在财务场景下等于不可用。

### 这样设计带来的三个好处

1. **可审计**：规则库是静态文本，可以被业务方逐条复核、签字确认
2. **可复现**：同样的输入永远得到同样的输出，出问题能定位到规则行
3. **可回滚**：改规则是改数据，不是改 prompt——不需要重新"调教"模型

## 1.4 双门模型：云端管「嘴」，本地管「手」

企业开发者常见的误解：调用了头部厂商的云端 API，厂商会替自己兜底一切安全。

实际上云端与本地之间有一条**不可混淆的物理边界**，可以理解为两道门：

### 第一道门 · 内容护栏（服务商云端）

- **约束对象**：模型的「嘴」——生成的文本与建议
- **控制权**：在服务商机房
- **能拦住**：违禁内容、暴恐文本、初级提权指令
- **拦不住**：结构化包装的恶意指令

⚠️ **关键点**：当模型通过 API 返回一段格式合法的 JSON 参数时，这道门会判定为**合法通过**。内容护栏做的是"内容审核"，不是"意图审核"。

### 第二道门 · 执行护栏（开发者本地）

- **约束对象**：操作系统的「手」——代码执行与系统 Shell
- **控制权**：在本地开发者手里
- **风险点**：如果本地代码写了 `os.system(模型建议)` 且一路同意，流量就从本地路由器发出去了

**责任判定**：攻击者为主机部署者。AI 无法人资格，人类承担全部责任。

### 治理铁律

> 永远把模型视为**「输入法」**（只提建议数值），
> 绝对不把它当成**「操作系统」**（不赋予直接系统指令权限）。

落地成三条硬性约束：

1. 所有文件写入，经本地**静态写死**的高阶白名单过滤
2. 所有网络请求，经本地固定端点表校验，禁止模型自由拼接 URL
3. 运行期切断模型对 `os.system` / `exec` / `eval` 的任何直接触碰

## 1.5 角色演进：谁在这个架构里变得不可替代

多智能体落地后，传统 CRUD 开发者的角色被稀释，但有一类角色反而变得关键：

| 角色 | 工作阵地 | 负责事项 | 在体系中的定位 |
|---|---|---|---|
| **多智能体编排架构师** | 提示词工程、状态机拓扑、规则固化 | 设计 Agent 通信 JSON 契约，梳理业务 If-Then 逻辑 | **业务灵魂赋予者（不可替代）** |
| **基础设施架构师** | 容器、内网数据库、API 网关 | 持久化、并发限流、灾备、密钥轮转、物理隔离 | 外部坚固容器提供者 |

**为什么第一个角色不可替代**：把模糊的企业制度翻译成刚性状态机，需要同时懂业务口径和技术约束。这个翻译过程无法自动化——它本身就是"左移确定性"里那个"人工梳理"的步骤。

## 本章小结

| 原则 | 一句话 |
|---|---|
| 责任归属 | 安全边界是责任要求，不是技术要求 |
| 左移确定性 | 确定性的建设放在设计期，不放在运行期 |
| 模型定位 | 只翻译，不计算 |
| 双门模型 | 云端管嘴，本地管手，第二道门是真正的防线 |
| 人工位置 | 目标不是无人化，是把人从重复核对转移到异常裁决 |
