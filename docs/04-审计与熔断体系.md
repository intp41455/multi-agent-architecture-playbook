# 04 · 审计与熔断体系

> 本章解决：**上了生产之后，怎么知道它今天做对了？**

---

## 4.1 生产环境最怕的不是"答错"

单测通过、Demo 漂亮、灰度没出问题——然后上线两周，悄悄积累了一批错误数据。

多智能体上生产，真正的风险是**"答错了没人知道"**。原因有三：

1. **结果自洽**：错误结论在链路内部逻辑自洽，单看输出看不出问题
2. **责任模糊**：出错后无法判断是哪一环失效
3. **静默失败**：异常被吞掉，日志里只留下"正常"

所以审计不是一个"功能模块"，而是**贯穿三个时间层次的体系**。

---

## 4.2 3-Tier Audit 总览

| 层级 | 时机 | 核心动作 | 产出 |
|:---:|---|---|---|
| **TIER 01** | 落地前（编码之前） | 数字孪生沙盘推演 | 准入判定 |
| **TIER 02** | 运行中（每次流转） | 三明治交叉验证 | 执行锁 |
| **TIER 03** | 周期性（月/季） | 复盘与闭环 | KPI 趋势 |

三个层级解决三个不同的问题：**能不能上、这次对不对、长期好不好**。

---

## 4.3 TIER 01 · 落地前：数字孪生沙盘推演

### 做法

1. 抽取过去 6 个月的**脱敏**真实数据作为基座
2. 人工构造 **50+ 极端边界案例**，例如：
   - 核心指标骤降（如入住率从 82% 跌到 50%）
   - 节假日排班真空（无人排班 + 无人请假，数据上"看起来正常"）
   - 多地负责人同时空缺
   - 同一员工同一天既有请假记录又有满勤打卡
3. 监察 Agent 在封闭沙箱中模拟执行，**比对 AI 裁决与人类历史处理结果**

### 准入标准（两条都要满足）

> - 常规场景一致性 **≥ 95%**
> - **且** 5% 极端边缘场景**全部**被安全拦截，并触发人工兜底预案

第二条是关键——很多方案只看第一条。**"边缘场景全部被拦住"比"常规场景准确率高"更重要**：前者说明系统知道自己的边界在哪，后者只说明它在熟悉区域表现好。

### 为什么必须有这一步

因为**异常分支的代码量占生产的 90%，但在 POC 里通常占 0%**。
沙盘推演是唯一能在编码前把异常分支翻出来的手段。

## 4.4 TIER 02 · 运行中：三明治交叉验证

每次任务流转时实时触发三道校验，**三层同时通过才放行**。

| 校验层 | 检查内容 | 典型失败案例 |
|---|---|---|
| **结构性校验** | 字段无缺失、类型正确、Schema 完全合规 | 金额字段返回了字符串 `"5,758.62"` |
| **逻辑自洽性** | 跨 Agent 数据勾稽关系无矛盾 | 报到率 100% 但打卡人数只有 80% |
| **时效新鲜度** | 时间戳未超期 | 用上个月的缓存数据算本月工资 |

### 为什么叫"三明治"

因为在数据流上，这三层是**夹在**上游产出与下游写入之间的：

```
上游 Agent 输出
      ↓
┌─────────────────┐
│ 结构 · 逻辑 · 时效 │  ← 三明治夹层
└─────────────────┘
      ↓
   执行锁释放 → 下游写入
```

> **准入标准**：三道防线全绿，下游写入模块才拿到执行锁；任一失败即刻原地刹车。

### 三个易被漏掉的细节

1. **逻辑自洽性需要跨 Agent 数据**——所以第 02 章的"通信契约必须带溯源信息"不是可选项
2. **时效性要用数据的时间戳，不是任务的时间戳**——一个刚创建的任务可能携带着陈旧数据
3. **校验失败要记录"失败的是哪一层"**——否则复盘时无法定位是数据源问题还是规则问题

## 4.5 TIER 03 · 周期复盘：反馈闭环与自进化

按月例行 + 按季战略复盘，跟踪两个核心指标：

| 指标 | 目标 | 为什么选它 |
|---|:---:|---|
| **建议采纳率** | ≥ 75% | 衡量 AI 输出是否真的被业务用起来（而不是"生成了但没人看"） |
| **合规审计误报率** | ≤ 2% | 衡量审计层是否在制造噪音（误报太多，业务会直接忽略告警） |

同时做三件事：

- **消除歧义规则**：把反复触发人工介入的规则，回头改清楚
- **季度评测新开源模型**：底座模型迭代快，定期评估性价比
- **规则库热插拔补丁**：规则更新不需要重启系统

### 一个反直觉的判断

**审计误报率过高，比漏报更危险。**

漏报是"没抓到"，误报是"狼来了"。当业务方被误报警告骚扰三周后，他们会形成"看到告警先忽略"的本能——这时候真正的 L3 告警也会被忽略。

所以宁可有少量漏报，也要把误报压到 2% 以内。

## 4.6 异常分级与熔断：L1 / L2 / L3

分级响应，避免"一刀切停机"（业务无法接受）和"一律放过"（风险无法接受）两个极端。

### L1 · 轻微异常（Minor Alert）

| 项 | 内容 |
|---|---|
| **触发条件** | 单点非关键字段缺失（如某日满意度调查未及时同步） |
| **系统动作** | 记录审计日志 → 向对接人推送轻度催办 → 次日凌晨自动重试 |
| **是否中断主流程** | 不中断 |
| **人工介入** | 不需要，自愈或顺延重试 |

### L2 · 一般异常（Moderate Risk）

| 项 | 内容 |
|---|---|
| **触发条件** | 输出格式损坏 / 字段与 Schema 不符 / 明显勾稽矛盾（如实发工资环比突变 20%） |
| **系统动作** | 立即挂起该子 Agent 工作流 → 自动重试 1 次 → 仍异常则**阻断向下一节点推送**，同时邮件 + 企微告警 |
| **人工介入** | 业务主管登录看板查看差额明细，点「人工确认放行」或「驳回重新计算」 |

**注意"重试 1 次"这个设计**：不重试会漏掉瞬时故障，重试多次说明这不是瞬时问题、而是真异常。

### L3 · 严重致命异常（Critical Emergency）

| 项 | 内容 |
|---|---|
| **触发条件** | 连续 3 天核心数据中断 / 多 Agent 输出严重逻辑悖论 / 检测到疑似提示词注入或越权操作指令 |
| **系统动作** | **全面物理熔断**：封锁所有对外 API、冻结本地写入脚本、系统回退至只读状态、触发紧急安全警报 |
| **人工介入** | **必须由系统架构师与业务分管负责人双人独立密钥**方可解除封锁 |

### L3 的设计要点：双人密钥

> **单点可以关掉系统，但不允许单点打开系统。**

熔断容易，解封难——这个不对称是刻意的：

- 熔断方向（安全方向）：任一检测器可独立触发
- 解封方向（风险方向）：需要两个不同角色的人各自输入密钥

这防止了两件事：一是单点误判导致长期停机；二是单点越权导致风险系统被重新放开。

## 4.7 审计轨迹：怎么留住证据

审计要能"回放"，前提是每次执行都留下完整轨迹。

| 要记录什么 | 用途 |
|---|---|
| 任务 ID + 上下游 Agent 标识 | 出错时定位到环节 |
| 每个 Agent 的原始输入与输出 | 判断是输入问题还是逻辑问题 |
| 生效的规则版本号 | 回答"上个月为什么算出这个数" |
| 审计裁决结果与理由 | 判断是"拦错了"还是"该拦" |
| 人工介入记录（谁、何时、放行/驳回） | 责任链追溯 |

**规则必须带版本号**——这是审计场景的刚需。薪酬规则改了之后，历史月份的数字应该是当时那一版规则算出来的。没有版本号，就无法回答"为什么张三上个月拿这个数"。

## 本章小结

| 层级 | 一句话 |
|:---:|---|
| TIER 01 | 边缘场景"全部被拦住"比常规准确率更重要 |
| TIER 02 | 三层校验夹在产出与写入之间，全绿才给执行锁 |
| TIER 03 | 误报率过高比漏报更危险 |
| L1/L2/L3 | 分级响应，不中断 / 挂起重试 / 物理熔断 |
| 双人密钥 | 单点可关系统，不可单点开系统 |
| 审计轨迹 | 规则必须有版本号，否则无法回溯历史 |
